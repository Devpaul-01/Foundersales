  title: Kith API
  description: |
    **Kith** is an AI-powered sales coaching and outreach platform for founders, 
    freelancers, and sales professionals. It combines opportunity discovery, 
    pipeline management, AI-driven practice sessions, calendar intelligence, 
    prospect relationship tracking, and team analytics into a single cohesive platform.

    ## Authentication
    All protected endpoints require a Supabase-issued JWT passed as a Bearer token 
    in the `Authorization` header. Tokens are obtained via `POST /api/auth/login` 
    or the Google OAuth flow.

    ## Workspace Context
    Most data endpoints are **workspace-scoped**. The server resolves the active 
    workspace from the authenticated user's `active_workspace_id`. Use 
    `POST /api/user/switch-workspace` or `POST /api/workspaces/switch` to change 
    the active workspace before making data requests.

    ## Rate Limits
    | Scope | Window | Max Requests |
    |-------|--------|-------------|
    | Auth endpoints | 15 min | 10 |
    | AI endpoints (chat, opportunities, goals, growth, calendar, practice) | 60 s | 30 |
    | Calendar AI sub-endpoints (prep, debrief, research) | 5 min | 10 |
    | Pipeline endpoints | 60 s | 120 |
    | Opportunity refresh | 60 min | 5 |

    ## Role Hierarchy
    `owner > admin > manager > member`

    Endpoints annotated with a minimum role require that role or higher.

    ## Async / Background Jobs
    Several endpoints trigger background BullMQ jobs after returning a synchronous 
    response. These include: opportunity refresh, onboarding voice-profile build, 
    calendar prep generation, post-session skill scoring, conversation analysis, 
    and growth card generation. The Bull Board admin UI is available at 
    `GET /admin/jobs` (requires `X-Admin-Secret` header).

        middleware. The full set of coach endpoints is unknown and has been omitted 
        from this spec to avoid fabricating behavior."
      action: "Upload routes/coach.js and regenerate the spec to fill this gap."

    - description: "There is no dedicated GET /api/workspaces/{id}/profile endpoint 
        to fetch the workspace_profiles row for a specific user. Profile data is 
        currently returned indirectly via GET /api/auth/me and onboarding routes."

    - description: "No endpoint exists to list all conversation analyses (the raw 
        scored records from POST /api/feedback). Analyses are visible only through 
        aggregated metrics and insights endpoints."

  inconsistencies:
    - description: "POST /api/workspaces/switch and POST /api/user/switch-workspace 
        are functionally identical (both switch active workspace). This creates two 
        entry points for the same operation. Consider deprecating one."

    - description: "GET /api/user/workspaces and GET /api/workspaces both return the 
        user's workspace list. Duplicate endpoint — one should be canonical."

    - description: "Practice badge awarding is fully in-process inside the /complete 
        handler, while skill scoring is delegated to a background job. Badge awarding 
        should arguably also be a background job for consistency and resilience."

    - description: "recordTokenUsage in goals.js uses userId as the first argument 
        (not workspaceId), inconsistent with chat.js, backgroundWorker.js, and the 
        corrected call in opportunities.js. Token usage attribution is split between 
        user and workspace scope."

    - description: "GET /api/pipeline/metrics and GET /api/pipeline?view=team both 
        return metrics. The former is a standalone metrics endpoint with no team mode."

  suggestions:
    - description: "Add a GET /api/auth/workspace-profile endpoint returning the full 
        workspace_profiles row for the active workspace. This would give the frontend 
        a single source of truth for the user's product/ICP/voice profile without 
        needing to merge data from /api/auth/me and onboarding status."

    - description: "Introduce a standard X-Request-ID or X-Trace-ID response header 
        using the existing traceId middleware. The trace ID is generated server-side 
        but not surfaced in responses, making correlation with server logs impossible 
        from the client side."

    - description: "Add a PATCH /api/user endpoint as a clean alternative to the 
        PUT /api/auth/me dual-purpose handler. Separating user table updates (name) 
        from workspace_profiles updates (product, ICP, etc.) would improve API clarity."

    - description: "Consider adding ETags or Last-Modified headers to the GET /api/opportunities, 
        GET /api/pipeline, and GET /api/growth/feed endpoints to enable client-side 
        conditional requests and reduce unnecessary data transfer."

    - description: "Opportunity status enum (pending → viewed → acted → sent → done) 
        and pipeline stage enum (new → contacted → replied → call_demo → closed_won | 
        closed_lost) overlap in semantics but are separate fields. A state machine 
        diagram in documentation would reduce integration confusion."

    - description: "The POST /api/practice/{sessionId}/message endpoint calls Groq 
        synchronously on every request with no local caching or debouncing. Under 
        the current 30/min AI rate limiter, a user sending messages rapidly could 
        exhaust their quota during an active session. Consider session-level rate 
        limiting distinct from the global AI limiter."

    - description: "There is no bulk-read endpoint for opportunities. The frontend 
        must paginate through multiple GET /api/opportunities calls to load a full 
        list. A cursor-based pagination approach (next_cursor) would be more efficient 
        than offset-based for large datasets."
